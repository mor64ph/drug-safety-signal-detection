# Deploying reportscope to Render

Written for whoever is doing the deployment, not for users of the tool.

The app is a Docker container serving a precomputed signal table from a parquet
file baked into the image, plus a Postgres database holding user accounts. There
is no writable state in the container: it can be destroyed and replaced with
nothing lost.

---

## Before you start

You need three things that are not in this repository.

**1. An SMTP provider.** Email verification and notification digests need one.
Resend, Postmark and Mailgun all have free tiers sufficient for UAT. You need a
host, port, username, password, and a From address on a domain you control.

Without SMTP configured the app writes messages to `data/outbox/` as `.eml`
files instead of sending them. That is correct for local work and useless in
production — testers cannot verify their addresses, so they cannot add
medications.

**2. An access code**, if UAT is to stay closed:

```
python scripts/make_access_code.py
```

Give the code to testers; put the hash in Render. The code itself never goes
into configuration.

**3. A finished diagnostics run.** Check before deploying:

```
python -c "import pandas as pd; d=pd.read_parquet('data/results/scored_pairs.parquet'); print(f'{int(d.diagnosed.sum()):,}/{len(d):,}')"
```

Every row should be diagnosed. Undiagnosed rows are hidden behind a toggle and
labelled, but shipping with most of the table unchecked means most of what a
user sees has not been examined for indication confounding — which is the
specific way this data misleads someone reading about their own medication.

## Deploying

### 1. Push to a Git repository

Confirm `.env` is not in the commit. It is in `.gitignore`, but check:

```
git status --short | findstr .env
```

Nothing should print.

### 2. Create the Blueprint

Render dashboard: **New > Blueprint**, select the repository. It reads
`render.yaml` and proposes a web service plus a Postgres instance. Apply.

`RXSIGNAL_SECRET_KEY` is generated by Render and then kept. Do not replace it
later: changing it signs every user out and invalidates pending password-reset
links.

### 3. Set the secrets Render cannot generate

Dashboard > service > **Environment**. These are marked `sync: false` in
`render.yaml` precisely so they are never committed:

| Variable | Value |
|---|---|
| `RXSIGNAL_ACCESS_CODE_HASH` | from `make_access_code.py` |
| `RXSIGNAL_ADMIN_CODE` | any long random string; guards `/admin/analytics` |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` | from your provider |
| `APP_BASE_URL` | your real URL, e.g. `https://reportscope.onrender.com` |

`APP_BASE_URL` must be exact. It builds the links inside verification and
password-reset emails, and a wrong value produces links that appear to work and
lead nowhere.

`OPENFDA_API_KEY` is only needed if you refresh data on the host. The shipped
image already contains the scored table.

### 4. Deploy and watch the first boot

`autoDeploy` is off, so trigger it manually. In the logs you should see:

```
[entrypoint] applying database migrations
[entrypoint] starting server
INFO serving 33,852 pairs across 361 drugs
INFO access gate: ENABLED (hashed code)
INFO listening on 0.0.0.0:8000
```

A `WARNING` about undiagnosed rows means the diagnostics run did not finish.

The container refuses to start if `RXSIGNAL_SECRET_KEY` is unset while the gate
is off, because that combination is a public deployment whose sessions die on
every restart.

### 5. Verify

```
curl https://YOUR-URL/healthz
```

Expect `{"status":"ok","drugs":361,"pairs":33852}`. Then in a browser:

1. The access gate challenges you
2. The code admits you
3. Register with a real address; the verification email arrives
4. The link verifies; the banner disappears
5. Add a drug; it appears with its bias flags
6. `/admin/analytics` refuses without `?code=`

If the verification email does not arrive, check the provider's dashboard
before the application logs — the app logs user IDs and outcomes only, never
addresses or message bodies.

## The notification digest job

Notifications accumulate in the database whether or not anything emails them.
Add a Render **Cron Job** using the same image and environment:

```
Command:   python scripts/send_digests.py
Schedule:  0 9 * * 1          # Mondays, 09:00 UTC
```

Weekly rather than daily is deliberate. These are reporting-pattern changes,
not urgent findings, and a daily email about drugs someone takes every day
trains them to ignore it.

## Refreshing the data

The shipped snapshot is fixed. To update it:

```
python run.py --score      # fetch, score, label, diagnose
python run.py --validate   # 22 controls must pass
```

Then update `DATA_AS_OF` in `src/app.py`, rebuild, redeploy.

`--validate` is not optional. It checks the pipeline against known answers —
statins and rhabdomyolysis at ROR 12.96, clozapine and agranulocytosis, several
boxed warnings. If those move, something upstream changed and the rest of the
numbers are not trustworthy either.

The Databricks pipeline in `databricks/` is the eventual replacement for this
manual path.

---

## Rolling back

Render keeps previous deploys. **Manual Deploy > pick an earlier commit.**

A rollback does not undo a database migration. Migrations here are additive, so
an older image runs against a newer schema without harm, but check before
relying on it.

---

## What is not set up

Deliberately absent, listed so nobody assumes otherwise:

- **Backups.** Render's Postgres plans include them; confirm the retention on
  the plan you chose.
- **Error tracking.** Unhandled exceptions log to stdout and are visible in
  Render's log viewer. No Sentry.
- **Custom domain and its TLS.** Render terminates TLS on its own domain.
- **Staging.** One environment. For UAT with a known group that is defensible;
  before a public launch it is not.
